# 14 — A language server that runs the compiler, not a copy of it

Date: 2026-02-14
Status: accepted

## Context

An editor wants four things from a language: diagnostics as you type, a
description of the name under the cursor, the place where that name is declared,
and a formatting pass. UMAY's command line already produces all four:

- `umay check` runs the whole frontend and reports diagnostics.
- `umay metadata` lists what a program declares.
- `umay fmt` rewrites whitespace.

The obvious way to build `umay lsp` is to keep an incremental model in the
server — a parse tree per open file, updated on each keystroke — because that is
what a language server is usually described as being.

## Decision

The server holds the text of each open document and nothing else. Every request
calls the same library functions the command-line commands call.

There is no incremental cache and no second type checker.

## Why

Three reasons, in order of how much they mattered.

**Drift is the failure mode that hurts.** A server with its own parse and its own
idea of what a name means will disagree with the compiler eventually. When it
does, the editor says the file is fine and the build says it is not, and the user
has to work out which one lied. Reusing `analyze_source` makes that disagreement
impossible: the squiggle and the build failure are the same code path.

**The cost is affordable.** Re-checking a UMAY file takes single-digit
milliseconds. Incremental machinery costs a cache, a diff, and a class of bugs
where the cache is stale — and it buys nothing at this size. That trade may be
worth revisiting for a large project; the honest thing is to say so here rather
than pretend it will scale forever.

**Building it last made it small.** Formatting, metadata and JSON diagnostics
were written and tested on their own first. The server is 600 lines because the
hard parts were already done and already had tests.

## Consequences

**Positions need converting.** The protocol counts lines from 0 and columns in
UTF-16 code units; the compiler counts bytes from 0. `lsp/position.rs` holds
every conversion. The UTF-16 detail is not cosmetic: a line with an emoji or an
accented letter has more bytes than units, and counting bytes puts the caret in
the wrong place on exactly the lines where a reader is most likely to be
confused already. There is a test for this.

**A request re-parses the file.** A hover is a parse and a metadata walk. That is
why completion offers what the file declares rather than a resolved scope-aware
list: scope tracking would need the incremental model this ADR rejects, and a
list of the file's own declarations is what a caller mostly wants while typing.

**`documentSymbol` ranges come from a name search.** The outline points at the
first whole-word occurrence after a declaration keyword. A symbol generated by a
macro has no such occurrence and falls back to the top of the file, which is
visible rather than silently wrong.

**The JSON layer is written out by hand.** The protocol needs objects, arrays,
strings and integers and nothing else. Writing it out keeps the output reviewable
and the crate dependency-free; the risk is that a case is missing, which is why
`jsonrpc.rs` has its own round-trip tests including surrogates and multi-byte
text.

## Modules and the buffer's path

The checker resolves `mod name;` against the directory of the file being
compiled, so the server has to know where the buffer lives. It therefore keeps
the path from the document's `file:` URI and hands it to the compiler as the
source name, percent-decoded. A buffer with any other scheme has no directory,
so it is checked under a placeholder name and its modules are missing -- the
honest result, since there is nowhere to look.
