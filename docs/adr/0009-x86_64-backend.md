# ADR 0009: The x86_64 backend

- Status: accepted
- Date: 2025-11-07
- Phase: 5

## Context

UMAY has had a front end and a checked MIR since phase 4, but nothing that turns
a program into something a computer can run. Phase 5 is the point where the
language first becomes executable, and that makes it the point where the
backend's shape is fixed.

The constraint from ADR 0002 is that there is no LLVM and no Cranelift: the
instruction selection, register allocation and object format are UMAY's own
code. ADR 0002 gave the reason — a compiler that cannot be debugged end to end
is not a compiler this project can own — but it left the internal design open.

Two questions had to be answered before writing code:

1. How much of the machine does each stage know?
2. Where does the backend stop?

## Decision

### The pipeline

```
MIR (checked, optimised)
  → layout        sizes, alignments, SysV eightbyte classification
  → frame         one stack slot per MIR local
  → isel          MIR → machine IR, with virtual registers
  → regalloc      linear scan with spilling
  → asm           AT&T text
  → as / cc       the system assembler and linker
```

Each arrow is a separate module with its own tests, and each stage only knows
the model the stage below it needs. `layout` does not know about instructions;
`isel` does not know about physical registers; `regalloc` does not know about
MIR.

### The machine model is a subset, built on demand

`machine.rs` describes only the instructions UMAY actually emits: `Move`,
`Alu`, `Cmp`, `SetCc`, `Test`, `Jmp`, `Jcc`, `Call`, `Ret`, `Push`, `Pop`,
`Lea`, `Load`, `Store`, `SignExtendAcc`, `Label` and `Comment`. There is no
model of every x86_64 instruction, and there never will be.

An instruction is added when a language construct needs it, together with the
test that construct needs. This is the only way to keep a hand-written backend
honest: every instruction in the model is reachable from a program in the test
suite, so nothing is dead weight and nothing is untested.

### Locals live on the stack; expression values live in virtual registers

Every MIR local gets a stack slot in `frame.rs`, sized and aligned from its
type, at a fixed offset from `%rbp`. Expression temporaries are produced into
virtual registers in `isel`.

This split is what makes `regalloc` a real pass rather than a bookkeeping
exercise. If everything were a stack slot, register allocation would have
nothing to do and could not be tested; if everything were a virtual register,
debugging a wrong answer would mean reasoning about allocation and selection at
the same time.

### Linear scan, with spilling

`regalloc.rs` computes one live interval per virtual register over the function's
linear block order, then walks intervals in order of start, assigning the first
free register that fits.

Two details matter:

- An interval that **spans a call** cannot use a caller-saved register, because
  the callee is free to destroy it. The allocator excludes those registers for
  such intervals rather than saving them around calls.
- When no register is free, the interval with the furthest end is spilled. A
  spill is not a new concept in the pipeline: a virtual register whose location
  is `Location::Stack` already has a stack slot, and `rewrite_registers` points
  every use and definition at that slot.

### Two-address fixes happen after allocation

x86 cannot copy memory to memory, and a store's source must be a register or an
immediate. But whether a value ends up in a register or a slot is not known
until allocation has run. `rewrite_registers` therefore rewrites a spilled
`Move` or `Store` into a load through `%rax` plus the original instruction.

This is the one place where a single source instruction becomes two machine
instructions, and it is deliberately kept in `regalloc` rather than pushed into
`isel`, because `isel` cannot know whether it will be needed.

### One shared epilogue

Every `Return` and `Unreachable` jumps to a single epilogue label at the end of
the function, numbered past the block labels so it cannot collide. The epilogue
restores the callee-saved registers and executes `leave; ret`.

Returning directly from each `Return` would be shorter, but it would duplicate
the teardown and, if a path forgot it, corrupt the stack in a way that is very
hard to trace back. One `jmp` per return is a price worth paying for a frame
that can only be torn down one way.

### The backend stops at assembly text

`umay build` writes `.s`, runs `as`, and links with `cc -no-pie`. UMAY does not
emit an ELF object itself and does not contain a linker.

The reason is that an object file is a specification of its own — sections,
relocation types, symbol tables — and implementing it correctly is a project in
itself, with no bearing on whether UMAY programs are correct. The system
assembler already encodes relocations from text, and the system linker already
knows where the C library and the startup objects live. Using them means the
backend is responsible for exactly one thing: converting a checked program into
the instructions that compute it.

`-no-pie` is used because the generated code addresses symbols absolutely.
Position independence is a later concern, and pretending to support it now would
mean either a relocation the text form cannot express or a silently wrong
address.

### A construct without code generation is a diagnostic

When `isel` meets something it cannot select — returning a large aggregate by
value, calling a function through a value, a float constant — it returns an
error and `codegen_source` turns it into `E3001`, naming the function.

The alternative, emitting whatever is convenient, produces a program that
silently computes the wrong answer. A missing feature that says so is worth far
more than a feature that appears to work.

## Consequences

### What works today

The end-to-end tests in `compiler/tests/phase5_codegen.rs` compile, link and run
real programs. Verified behaviour includes:

- integer arithmetic at the type's own width, so `200u8 + 100u8` is 44;
- signed division and remainder, with the remainder taking the dividend's sign;
- `if`/`else`, `while`, nested loops;
- function calls, recursion, and more than six arguments (which go on the stack);
- struct construction, field reads and field writes;
- casts, booleans, and comparisons;
- identical results at `-O0`, `-O1`, `-O2` and `-O3`.

### Known gaps

These are reported as `E3001`, not silently miscompiled:

- returning an aggregate larger than two eightbytes by hidden pointer;
- indirect calls through a function value;
- float constants and floating-point arithmetic;
- aggregate arguments passed by value on the stack;
- position-independent code.

### Costs accepted

- Linear scan is worse than graph colouring on register pressure, but it is
  about a page of code and can be replaced later without touching `isel`.
- One stack slot per local means large frames for programs with many
  temporaries. MIR temporaries are already limited by the front end's expression
  nesting, so this has not been a problem yet.
- The argument shuffle between registers parks values on the stack rather than
  finding a cycle-free order. It costs a few instructions per call. A naive
  in-place shuffle was tried first and produced wrong answers, because writing
  `%rsi` destroyed an argument still waiting there; a correct in-place version
  needs cycle detection, which is a larger change than the cost justifies today.
